# review-design: ペライチの設計ビュー

4枚の図と「どこを見るか」の短い表からなる **1ページ** を作る。A4 1枚に収まり、スクロールせずに読み切れること。

| セクション | 図 | 答える問い |
|---|---|---|
| 1. 要件 | `flowchart` — actor → 新しくできること → 成果 | 誰の何が変わるのか |
| 2. 基本設計 | `flowchart` — コンポーネント図 | どこに置かれ、何に依存するのか |
| 3. 詳細設計 — 構造 | `classDiagram` | 型・クラスとその関係はどうなるのか |
| 4. 詳細設計 — 振る舞い | `sequenceDiagram` | どの関数がどの順で呼ばれるのか |
| 5. レビューで見るところ | 表（3〜5行） | どこを疑って読むべきか |

読み手は差分そのものは既に持っている。持っていないのはその *形* である。このページは形だけを提供し、それ以上はやらない。

## なぜこの構成なのか

これから誰かが PR をレビューする。有用なレビューに辿り着くまでに4つの問いが立ちはだかる — これは何のためか / どこに位置するのか / 何がどの順で走るのか / どこを重点的に見るべきか。文章はこれらにゆっくりとしか答えられないが、図は一目で答える。

セクション3と4は意図的に対になっている。クラス図は *構造* — 何が存在し、どう関係しているか — を示すが、実際に何が起きるかは示さない。シーケンス図は *呼び出し* を示すが、型の形は暗黙のままになる。レビュアーには両方が必要で、どちらも他方の代わりにはならない。だから両方に枠を与える。

1ページという上限は飾りではない。スクロールを強いられたレビュアーは結局ドキュメントを読んでいることになり、それこそが避けようとしていたものである。そして1セクション1枚しか許されないことが、気づいたこと全部ではなく「本当に重要な1枚」を描かせる。

これは地図であって、コードの代わりではない。そのことをページに明記し、図だけで PR を承認できるような書き方は決してしないこと。

## 原則

**差分を光らせる。** システム全体の正確な図はここではほとんど価値がない — レビュアーはシステムを既に知っている。知らないのは「今回何が変わったか」である。どの図でも新規/変更/削除の要素にマークを付け、変更が読み取れるのに必要な分だけ既存要素を残す。レビュアーが 🆕 を探し回るようなら、文脈を減らして描き直すこと。

**実在の関数名を書く。** セクション3と4がスペースに見合うのは、実際の識別子を載せている場合だけである — `注文を作る` ではなく `create_order(user_id, items)`。その名前こそがレビュアーを図からコードへ飛ばす経路になる。大文字小文字やアンダースコアも含め、そのまま書き写すこと。

**追加せず、畳み込む。** 5枚目の図が答えになることはまずない。状態はシーケンス図の `Note over` 注記に、スキーマ変更はコンポーネント図のラベル付きデータストアノードに、旧コードパスは同じ図の 🗑 付き破線分岐にする。畳み込めば1ページを保てるが、追加すれば失う。

**誰にも読めない図は、無い方がましである。** ノード15個程度（シーケンス図なら participant 7個）が上限。それを超えたら抽象度を上げ、複数の箱を1つにまとめること。

**確認したことだけを主張する。** セクション5はこのページが実害を出しうる場所である — 自信たっぷりの誤った指摘はレビュアーを間違った方向へ送り出すし、精密に見えるせいで信用されてしまう。コード上で検証したことは平叙文で書き、それ以外には `未確認:` を付けて「何が分かれば決着するか」を書くこと。安く決着がつくなら（テスト1本、1行スクリプト）、実際に走らせること。

不在の主張は特に段落を割く価値がある。いつも間違うのがこれだからだ — 「テストが無い」「マイグレーションが無い」「呼び出し元が無い」。差分は、何かが *存在しない* ことを何も教えてくれない。それが分かるのは検索した時だけであり、「空振りした検索」と「やらなかった検索」は別物である。書く前にリポジトリを grep して（テストファイル、フィクスチャ名、パラメトライズされたケース、マイグレーションディレクトリ）、検索した語をその行の確認印に記録すること: `✓探索(alembic)`。検索できないなら、その行は `⚠未確認` になる。

**ユーザーの言語で書く。** キャプションと見出しはユーザーが話している言語に合わせる。識別子はそのまま。

## ワークフロー

### Step 1 — 対象を決める

| モード | 起動方法 | 読むもの |
|---|---|---|
| PR | `pr 123` | `gh pr view 123 --json title,body,url,headRefName,baseRefName` と `gh pr diff 123` |
| Branch | `branch main..HEAD` | `git diff --stat <spec>`、`git diff <spec>`、`git log --format='%s%n%b' <spec>` |
| Working | `working` | `git status --porcelain`、`git diff`、`git diff --cached`、および未追跡ファイルの内容 |
| Files | `src/order/*.ts ...` | 指定されたファイルの全文 |

引数が無い場合は聞かずに選ぶこと — ユーザーは手間を省くためにここへ来た。この順で解決する: 未コミットの変更がある → `working`、そうでなくブランチがベースより進んでいる → `branch`、そうでなくオープンな PR がある → `pr`。どのモードで描いたかをページに明記すれば、推測が外れていても一目で分かり、訂正も安く済む。どれにも当てはまらない時だけ質問する。

**Files モードには差分が無い** ので、マーカーは適用しない。構造をありのままに描くこと: そのコードが何のためのもので、どう配置され、どんな型が存在し、典型的な呼び出しがどう流れるか。

### Step 2 — 明示された意図を集める

この順で読む: PR のタイトルと本文 → リンクされた Issue（本文中の `#\d+`、`gh issue view N --json title,body`、最大2件）→ コミットの件名と本文。

人間が書いた意図は、こちらが推論したどんなものより優先される。特にコミット本文には業務上の理由（「経理が手作業で突合している」）が書かれていることが多く、それはまさにセクション1が必要としていて、差分からは得られないものである。明示された意図が存在しない場合はコードから推論し、出典行に `[推測]` と記すこと。`docs/` を漁りに行かないこと。遅いうえに、たいてい古い。

### Step 3 — 変更を読む

差分はファイル単位ではなく *意味* 単位でまとめること: 「注文作成APIの追加」はひとまとまりだが、`OrderController.ts` はそうではない。

ノイズは飛ばす: ロックファイル、`dist/` `build/` `vendor/`、生成コード、スナップショット、フィクスチャ、画像、フォーマット揺れ。巨大な差分では先に `--stat` を使い、拾い読みで全部を眺めるのではなく本質的なファイルを全文読むこと。

差分がそのままでは渡してくれないものが2つあるので、意識して探すこと:

- **型の全体像** — 変更の周囲にどんなクラス/構造体/インターフェースがあり、何を保持し、どのメソッドが移動または新設されたか。変更行だけでなくクラス本体を読むこと。新しいメンバーがそこに属するべきか判断するには、レビュアーは周囲の形を知る必要がある。
- **呼び出し経路** — 代表的なリクエストを1つ、エントリポイント（ハンドラ、コマンド、ジョブ）から副作用まで追い、実際の関数名と分岐の位置を控えておく。これがセクション4に描くものである。

読みながら、セクション5の候補を集めること:

- 新しい外部依存や外向き呼び出し（ネットワーク、DB、ファイルシステム、サブプロセス）
- トランザクションとロックの境界
- エラー経路、および明らかに欠けているエラー経路
- 並行処理、非同期の順序、リトライ、冪等性
- スキーマや永続化される形の変更、およびマイグレーションの有無
- 認証/認可のチェック、シークレット、個人情報
- この変更が壊す既存の呼び出し元とテスト

### Step 4 — 4枚を描く

**1. 要件** — 誰が何をできるようになり、それがどんな問題を解くのか。actor → 新しくできること → 業務上の成果、という小さな `flowchart`。一番右のノードには *業務上の* 成果を置くこと。レビュアーがコードを突き合わせる相手はそれである。ユーザーから見える変化の無い純粋なリファクタリングなら、代わりに構造上の約束を描く（「同じロジックが 2 箇所 → 1 箇所」）。本当に1文で言い切れるなら、その1文を書いて図は省く — 残り3枚だけでも1ページ分の価値はある。

**2. 基本設計** — `flowchart` によるコンポーネント図: 変更がどこに位置し、何に依存し、どのデータストアや外部システムに触れるか。この図が他の2枚の位置づけを与えるので、粒度はモジュール/サービスに保ち、詳細はセクション3〜4に任せること。

**3. 詳細設計 — 構造** — 変更が触れる型の `classDiagram`。関係と、重要なメンバーを載せる。クラスだと分かる程度には未変更のメンバーも含め、何が移動したかをマークすること。変更が階層をまたぐ場合（何かが親クラスに引き上げられた、インターフェースが抽出された）、その階層 *こそが* 本題である — 描いて、各メンバーが今どこにあるかを示すこと。

クラスを持たないコード（手続き的なモジュール、フック、スクリプト、SQL）では、同じ発想を `flowchart` で描く: モジュールを箱、エクスポートされた関数をメンバー、import をエッジとする。この枠の要点は「何が存在し、どう関係しているか」であって、`classDiagram` というキーワードそのものではない。

**4. 詳細設計 — 振る舞い** — 代表的な呼び出し経路1本の `sequenceDiagram`。メッセージには実際の関数名を書く。失敗分岐には `alt` を使うこと — レビューで面白いのはたいていエラー経路である。別の図が必要になりそうなものは畳み込む: 新しい状態は `Note over`、トランザクション境界は `Note over A,B`、リトライは `loop`。

最も単純な経路ではなく、最もリスクの高い経路を選ぶこと。2つの経路がどちらも重要なら（作成とキャンセルなど）、リスクの高い方を描き、もう一方はセクション5で1行触れる。

### Step 5 — 図が描画されることを確認する

構文エラーのある Mermaid ブロックは GitHub 上で赤いエラーボックスになり、そうなるとこのページの価値はゼロ以下になる:

```bash
python3 scripts/check_mermaid.py <output.md>
```

このスクリプトは、`subgraph`/`end` の不整合、不正なノードID、ラベルを壊す未クォートの文字、未定義の `classDef` への `class` 参照、読める限界を超えたノード数、`color:` が明示されていない `classDef`（ダークモードでラベルが消える）を報告する。報告されたものは全て直すこと。

実際に描画して確認するには `--render` を付ける。`mmdc` がインストールされていればそれを、無ければ `npx -y @mermaid-js/mermaid-cli` を使う。npx 経路は初回にブラウザをダウンロードする（数分かかって遅い）が、以降は速い。珍しい構文を使ったので実際に描けることを確かめたい時には、その価値がある。

### Step 6 — 引き渡す

Markdown ファイルを1つ書く。既定ではカレントディレクトリに `review-design-<slug>.md`（`pr123`、`branch-main-HEAD`、`working`、`files`）、あるいはユーザーが指定した場所。そのうえでパスを1行で伝えること — チャットで変更内容を説明し直さないこと。説明を読まずに済むようにこのページが存在するのだから。

## 差分のマーキング

主たるシグナルは絵文字マーカーで、色は補助である。絵文字はどのレンダラーでもどちらのテーマでも生き残るが、`classDef` の塗りはそうではない。

- 🆕 新規 / ✏️ 変更 / 🗑 削除 / マーカー無し = 既存の文脈

図の種類ごとのマーカーの置き場所（以下4形式はいずれも Mermaid 11 で描画を確認済み）:

| 図 | マークの付け方 |
|---|---|
| `flowchart` | ラベル内: `SVC["🆕 OrderService"]`、加えて `classDef` の色 |
| `sequenceDiagram` | `participant PAY as 🆕 PaymentClient`、およびメッセージ上: `API->>SVC: ✏️ create_order(...)` |
| `classDiagram` | クラスラベル構文 `class Parameter["✏️ Parameter"]`、メンバーは **末尾に付ける**: `+help str 🆕` |
| `stateDiagram-v2` | 状態ラベル内、加えて `classDef` の色 |

`classDiagram` では、メンバー行の *先頭* にマーカーを置くと `+name : type` の整形が壊れる — 必ず末尾に置くこと。

`flowchart` と `stateDiagram` では色を付ける。`fill:` には必ず `color:` を併記すること。さもないと GitHub のダークテーマでラベルが読めなくなる:

```
classDef added fill:#dafbe1,stroke:#2da44e,stroke-width:2px,color:#1a1a1a
classDef changed fill:#fff5d6,stroke:#bf8700,stroke-width:2px,color:#1a1a1a
classDef removed fill:#ffe2e0,stroke:#cf222e,stroke-width:2px,color:#1a1a1a
classDef context fill:#f0f2f4,stroke:#9aa4ae,color:#3a3a3a
class API,SVC added
```

凡例はヘッダー行に、1回だけ書く。

## 効いてくる Mermaid のルール

以下は実際に起きる失敗である。それ以外と各図のテンプレートは `references/mermaid-patterns.md` にある。

- **ノードID**: ASCII の英字・数字・`_`、先頭は英字。日本語や記号は *ラベル* に入れる。
- **`(` `)` `,` `:` `[` `]` `{` `}` `/` を含むラベルは全てクォートする** — `API["POST /orders (v2)"]`。クォートして間違いになることは無いので、既定でクォートすること。
- **ラベル内の改行**: `\n` ではなく `<br/>`。
- **`end` は常に小文字**。`subgraph` / `alt` / `opt` / `loop` / `par` / `rect` には必ず対応する `end` が要る。
- **エッジラベル**: `A -->|"作成 (非同期)"| B` — これもクォートする。
- **classDiagram のジェネリクス** は `~` を使う: `List~Order~`、`List<Order>` は不可。

````markdown
# 設計ビュー — <対象>

**一行で言うと:** <この変更が何をするのか、1文>

## 1. 要件

```mermaid
<actor → 新しくできること → 業務上の成果>
```

*出典: <PR本文 | Issue #45 | コミットメッセージ | [推測]>*

## 2. 基本設計

```mermaid
<component view>
```

**読みどころ:** <図から読み取れないことだけ、2行以内>

## 3. 詳細設計 — 構造

```mermaid
<classDiagram>
```

**読みどころ:** <2行以内>

## 4. 詳細設計 — 振る舞い

```mermaid
<sequenceDiagram、メッセージは実際の関数名>
```

**読みどころ:** <2行以内>

## 5. レビューで見るところ

| # | 場所 | 何を見るか |
|---|---|---|
| 1 | `app/order_service.py:39-58` | 与信が残るのに注文が無い状態が起きうる ✓確認 |
| 2 | `tests/test_order_service.py:24` | 引数追加に追随せず `TypeError` で全滅 ✓実行 |
| 3 | `app/payment_client.py:73` | `void()` が全例外を握り潰す ✓確認 |
| 4 | `schema.sql:12` | `payments` のマイグレーションが無い ✓探索(alembic) |
| 5 | `app/config.py:6` | 鍵未設定が 503 として見える ⚠未確認(プロバイダの応答) |
````

どれかが薄くなっても5つのセクションは残すこと — セクション自体が「どこを見ればよいか」を読み手に伝えている。図にするほどの中身が無いセクションは、代わりに1行で済ませる（「既存の構成に変更なし」）。

セクション5はこのページが元を取る場所である。具体的なファイルと行を指し、何を見るべきかを書くこと。3〜5行、そこでのミスが高くつく順に並べる。

**各セルは1文、60文字程度に収め、末尾に確認印を付けること。** これは最も破られやすいルールである。どの行も根拠と帰結と留保を書きたくなり、3文書いた頃には表は再び文章になっている — それこそ読み手が逃れようとしたものである。セルの役目は、そのファイルを開かせることであって、開く手間を省いてやることではない。説明ではなく症状を書くこと: 「与信が残るのに注文が無い」の方が「与信成功後〜COMMIT前にプロセスが落ちると、与信は残るが orders に行が無く、夜間スイーパは注文行を見る仕組みなので回収できない」より優れている。長い説明が本当に必要な指摘なら、それは図に出すべき重要度である — `Note` として図に書き、行はそこを指させること。

その行をどこまで検証できたかは、レビュアーが必要としている情報である — 再現済みのバグと単なる勘とでは、割くべき注意の量が違う。ただしそれは *メタデータ* なので、2文目として書くのではなく、セル末尾の印で示す:

| 印 | 意味 |
|---|---|
| `✓実行` | 実際に動かして、その失敗を見た |
| `✓確認` | コードを読んで確認した |
| `✓探索(語)` | 検索して、本当に存在しないことを確かめた。検索した語を括弧に入れる |
| `⚠未確認` | 未検証 — 何が分かれば決着するかを括弧に書く |

印の無い行は未検証の推測として読まれるので、全ての行に印を付けること。

## 1ページに収める

目安の予算: 図4枚、各15ノード以内、図の外の文章は2,000〜2,500文字、セクション5は5行以内。

収まらない時は、この順で削る: 読み手が既に知っている文脈ノードを落とす → 抽象度を上げる → セクション5のセルを短くする → 残ったものをセクション5の1行に格下げする。何かを落として1行でそう断る方が、2ページ目を作るよりましである。

## 失敗パターン

- **5枚目の図。** 畳み込むか、セクション5の1行に格下げする。
- **メンバーの無いクラス図、文章メッセージのシーケンス図。** どちらの枠も実在の識別子を載せるために存在する。それが無ければただの飾りである。
- **変更が埋もれるアーキテクチャ図。** 文脈を減らし、差分を増やす。
- **図の下の段落。** 読み手は文章を読まないと決めてここに来た。2行書いたら止めること。
- **段落でできた表。** 3文×5行は、表の服を着た700文字の文章である。1セル1文、そして確認印。
- **根拠を2文目に書く。** 「…を再現済み」は印（`✓実行`）であって、文ではない。
- **調べずに書いた「X が無い」。** 先に grep して検索語を `✓探索(語)` に入れるか、`⚠未確認` と書く。
- **壊れた Mermaid。** GitHub 上の赤いエラーボックスはページの信頼性を破壊する。チェッカーを走らせること。
- **確認していない断定。** 検証するか、`未確認:` と書く。
- **差分の描き直し。** 変更ファイル1つにつき1箱をファイル順に繋いだものは設計図ではない。意味でまとめること。
